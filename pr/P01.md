# P01: Pilot hosting with encrypted off-site backups, error reporting, metrics, boot-time config and an E2E harness

## Summary

This builds on PR #27 (`claude/musing-wilbur-d67503`, commit `654e2ac`, which is included) and closes the production-readiness items that PRODUCTION-READINESS.md listed as blockers, as far as code and scripts can close them:

- **Backups:** nightly copies can now be encrypted with `age` and uploaded with `rclone` to any object store, and you can run a restore drill straight from an off-site copy. Off-site is off until configured. The private key never sits on the server.
- **Configuration:** the API declares and validates every environment variable it reads, and refuses to boot on a bad one.
- **Error reporting:** reports go to a Sentry-protocol DSN (no SDK), a JSON endpoint (ntfy) or the console. They come from request handlers, scheduler jobs, process crash handlers and both front ends. Both front ends show a plain-language recovery screen.
- **Metrics:** a Prometheus `/metrics` endpoint behind a bearer token, plus written alert rules mapped to the pilot's free alert services.
- **Migrations:** drizzle migration metadata is complete, and CI fails on schema drift.
- **E2E:** a Playwright harness runs against the production single-origin build with a temporary database. It has 3 specs and a CI job.

Nothing was deployed. No server, bucket, DSN project or alert account was created.

## What changed (by app)

### `deploy/pilot` and CI (PR #27 follow-up)
- `backup.sh`: optional off-site step.
  - **Turning it on:** set `SHARK_BACKUP_OFFSITE_REMOTE` (an rclone `remote:path`) and `SHARK_BACKUP_AGE_RECIPIENT` (one or more `age1…` public keys). Each copy and its manifest are then encrypted, uploaded to `<remote>/<kind>/`, and checked with `rclone check`. The output includes an `offsite_object=` line.
  - **Pruning:** off-site copies older than `SHARK_BACKUP_OFFSITE_KEEP_DAYS` (default 30) are deleted only after an upload succeeds.
  - **On failure:** `offsite=failed`. Every local copy is kept and local pruning is skipped. A nightly run pings `/fail` and exits 1. Pre-deploy and manual runs print a warning and exit 0, because their local copy is good.
  - **Unset:** prints `offsite=skipped` and otherwise behaves exactly as before.
  - **Refused before backing up:** only one of the two variables set, a malformed remote or recipient, or missing tools.
- `restore-drill.sh --from-offsite <object> --age-identity <file>`: downloads the copy, decrypts it, checks its SHA-256 against the manifest (`offsite_download=verified`), then runs the normal drill. The decrypted copy is deleted afterwards, also when the drill fails. `<object>` can be the `offsite_object=` line or a path under the configured remote.
- `provision.sh` installs `age` and `rclone`. Both scripts default `RCLONE_CONFIG` to root's config, because the systemd unit has no `$HOME`. `shark.env.example` documents the three new variables (placeholders only).
- `pilot-stack.yml` gets three new steps, and `config.ts`/`server.ts` are added to its triggers:
  - an encrypted upload through the real nightly unit to an rclone `local` remote, with a key pair generated in the job. It asserts the remote holds ciphertext and that a healthchecks stand-in got the success ping.
  - a drill from that off-site copy, signing in as the owner.
  - a forced upload failure (WebDAV on a closed port). It asserts the exit code, that local copies are kept, and the `/fail` ping. It also asserts that the pre-deploy copy goes off-site too.
- `ci.yml`:
  - `db:check-drift` step (earlier commit).
  - New `e2e` job after `verify`: Playwright browsers cached by version, report and traces uploaded on failure.
- PR #27 review: shellcheck (v0.10.0, `-S warning`) and `bash -n` were already clean. The one real gap was the manual, unencrypted off-site copy, now replaced by the above. `pull-backup.sh` still works unchanged; it picks `backup=` out of the longer output.

### API (`apps/api`)
- **`lib/config.ts`:**
  - Declares the OTP provider, credential and limit variables, plus `SHARK_ERROR_REPORTER`, `SHARK_ERROR_DSN` and `SHARK_METRICS_TOKEN`. `otp-delivery.ts` and `otp-limits.ts` read only `runtimeConfig`.
  - Refused in every environment: a provider selected without credentials, an unknown provider or reporter name, a non-numeric OTP limit, a malformed DSN.
  - Refused in production only: a non-HTTPS DSN, a metrics token under 32 characters.
  - Tests fail on any `process.env` read outside `lib/config.ts` and on any declared key missing from `.env.example`.
- **`lib/error-reporting.ts`:**
  - Providers: `none`, `console`, `http`, `sentry`. `auto` means DSN first, then endpoint, then console in development, otherwise none.
  - A report carries: the error type, the redacted message, parsed and redacted stack frames (in-app flag, no cwd, no query strings), release, environment, request id, route, tenant/actor ids, job, source. Nothing else.
  - Capped at 60 server reports a minute and, separately, 60 browser reports a minute, so public `/v1/client-errors` traffic cannot crowd out server errors. `flush(timeout)`.
  - The Sentry event's tags are request id, route, tenant/actor ids, job and source only. The pre-existing `http` reporter also still sends the branch scope it always sent.
  - The boot log names the reporter and whether metrics are on.
- **`lib/process-handlers.ts`:**
  - `unhandledRejection` is logged and reported, and the process keeps serving.
  - `uncaughtException` is reported, flushed for up to 2 s, then the process exits 1 in production. In development it only logs loudly, so `tsx watch` keeps running.
  - SIGTERM also flushes reports before exiting.
- **Scheduler:** a failing job is reported once, tagged `{job, source: 'scheduler'}`, on top of the existing failed `job_runs` row.
- **`POST /v1/client-errors`:**
  - Public. Exempt from the CSRF token, but a known Origin is required.
  - Body cap of 8 KB, enforced whether or not Content-Length is declared.
  - Zod schema shared from `@shark/contracts`.
  - Rate limits: 30/min per IP, then 300/min per signed-in tenant or one shared anonymous budget.
  - Redacted log line. Ids are collapsed out of SPA routes. The report is forwarded with `source: admin|member`. A new `PAYLOAD_TOO_LARGE` (413) error code.
- **`GET /metrics`:**
  - 404 unless `SHARK_METRICS_TOKEN` is set, then a bearer token compared in constant time. Prometheus text format.
  - Metric families: `http_requests_total{method,route,status}` (Hono route templates), `http_request_duration_seconds`, `job_runs_total{job,outcome}`, `job_last_success_timestamp_seconds{job}` (from `job_runs`, so it survives restarts), `outbox_undelivered_events`, `sqlite_db_size_bytes`, `data_filesystem_size_bytes`/`data_filesystem_avail_bytes`, process CPU and memory, `app_build_info`.
- **Redaction:** now also strips `shark_session`/`shark_csrf` cookie values, and keeps the credential's name (`password=[redacted]`; this was previously a literal `$1`).
- **Migrations:** `drizzle.config.ts` lists all 8 schema files. Snapshots 0014–0017 were derived from drizzle-kit's own snapshot and proven equal to 0013 plus what 0014–0017 apply. No applied SQL was touched. `db:check-drift` script and CI step.

## Decisions and assumptions
- **Off-site upload failure fails only the nightly run.** For a nightly run, systemd and healthchecks.io both show the failure. A pre-deploy or manual run keeps its good local copy and warns, so a bucket outage cannot block a deploy. In every case local pruning stops until an upload succeeds, so the newest local copies are never deleted while off-site is broken.
- **Key custody:** the server holds only public keys. Several recipients are allowed (e.g. the owner plus the maintainer). For drills and restores, the private key is brought into `/run` and shredded afterwards.
- **Retention:** erased members persist in backups for up to 14 days locally and 30 days off-site (the defaults). The privacy notice must state that window. After a full restore, re-apply the erasures completed after the copy's timestamp. Documented in PILOT-HOSTING and PRODUCTION-READINESS.
- **Disk and memory alerts for the pilot** use DigitalOcean Monitoring (free) instead of introducing a metrics scraper. Prometheus rules are written for when one exists. Because the app's `job` label collides with Prometheus's scrape `job` label, the rules use `exported_job`.
- **The client-error contract lives in `@shark/contracts`,** so the API validates exactly what the apps send. Each app keeps a thin module and its own recovery screen styled for its surface.
- **Reports use `keepalive` fetches,** so they leave even if the person taps Reload at once. Playwright cannot see keepalive requests, and its `page.route` interception swallows them. The client-error spec therefore blocks the chunk via CDP `Network.setBlockedURLs` and asserts on the server log, which is stronger evidence anyway.
- **Member ids are `mbr_`** (the spec says `mem_`). The label test refuses `ten_|usr_|mem_|mbr_|br_`.
- **E2E runs with scheduled jobs off** (deterministic data), service workers blocked (the build under test is what loads), and `SHARK_ERROR_REPORTER=console`.
- **Dependencies:** only `@playwright/test` 1.65.1 (dev, in `@shark/e2e`). No runtime dependency was added: metrics and the Sentry protocol are hand-written (about 150 and 100 lines).

## Known limitations / follow-ups
- **Operator actions are still needed** (out of scope for this phase):
  - create the bucket and age key, and set the two backup variables;
  - run `restore-drill.sh --from-offsite` on the real host;
  - connect an error destination (DSN or ntfy) and the UptimeRobot, healthchecks.io and DigitalOcean Monitoring alerts;
  - optionally set `SHARK_METRICS_TOKEN` and a scraper.
- **The privacy notice must state the backup retention window** (30 days with the defaults). Keep an off-server log of completed erasures for re-application after a restore.
- **Stale or failing scheduler jobs:** a stale job is only detectable once a metrics scraper exists. Without one, failures still arrive as error reports.
- **E2E covers 3 flows,** as scoped. P08 expands it.
- **Noticed, not fixed:** when a lazy route chunk fails to load, TanStack Router first renders the error component with React error #31 ("object with keys {default}") before the real error. Only the final error is reported and shown; worth investigating in P09.
- **The two apps' `lib/error-reporting.ts` are near-identical thin wrappers** (each imports its own `ApiError`/`OfflineError`). The shared logic is in `@shark/contracts`.
