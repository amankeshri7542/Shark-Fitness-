# Integrate P02–P07 into one product: payments, website, member app, staff security, member core, engagement

## Summary

This branch, `integration/features`, merges the six phase branches built in parallel on top of `phase/P01-prod-readiness` (2c15353). Every phase's features, routes, migrations and tests are kept. One product now serves:

- the public website at `/` (P03);
- the installable member app at `/app/`: Razorpay test-mode checkout (P02), QR pass, safe waitlist, credit packs, progress photos (P05), push and offline use (P04), messaging and community (P07);
- the staff console at `/admin/`: MFA, step-up, sessions, webhooks (P06), reconciliation (P02), reception scanning (P05), inbox, tasks, broadcasts and coaching (P07);
- the API at `/v1`.

The work went in this order:

1. Six `--no-ff` merges in the given order.
2. Conflicts resolved so both sides' intent survives.
3. Migrations made linear.
4. The cross-phase seams the implementers listed wired up, with tests.
5. The failures that only appear once the branches are combined fixed.

Payments stay in Razorpay test mode. Nothing was deployed, sent or charged.

**Security middleware (P02 × P03 × P06).** The webhook exemption (P02), the public-form token exemption (P03) and the CSP-report exemption (P06) live side by side.

Production single-origin smoke. Since P06, production also requires `SHARK_MFA_ENCRYPTION_KEY`:

```bash
TMP=$(mktemp -d)
SHARK_DB=$TMP/shark.db pnpm -F @shark/api migrate && SHARK_DB=$TMP/shark.db pnpm -F @shark/api seed
cd apps/api && NODE_ENV=production PORT=8788 SHARK_SERVE_STATIC=true SHARK_DB=$TMP/shark.db \
  SHARK_ALLOWED_ORIGINS=http://localhost:8788 SHARK_PUBLIC_ORIGIN=http://localhost:8788 \
  SHARK_PASS_SECRET=$(openssl rand -base64 48) SHARK_MFA_ENCRYPTION_KEY=$(openssl rand -base64 32) pnpm start
```

Then open `/` (website), `/app/` (`aman@sharkfitness.in` / `shark1234`, gym `shark`) and `/admin/`. The owner `owner@sharkfitness.in` meets the two-step enrolment gate.

## Known issues / follow-ups

- **Razorpay CSP origins** are P06's list, still unverified against the live sandbox modal. Not added: `cdn.razorpay.com` images and regional `api-sg.razorpay.com`. Confirm in a test-mode session before go-live.
- **Failed online attempts do not create P07 "failed payment" tasks.** P02 records them on payment intents, not as failed payments, and the member is usually retrying; dunning chases overdue invoices. If wanted, the generator could read failed intents older than N hours.
- **Message attachments** use P07's path-signed URLs and do not go through P05's `media_objects` and `/v1/files/:id`, which have viewer-bound URLs and the quota. Unifying them is feature work.
- **Fonts:** the latin subset has no ₹ glyph, so it falls back to the system face, as it did with Google Fonts before. A tiny ₹-only subset would fix it.
- **Member precache** is at 695.8 of 700 KiB. The next screen added to the shell will need the budget revisited.
- **Payment-link creation** is not step-up guarded, by decision: it sends nothing and moves no money.
- **Production config:** `.env.example`, Render and the pilot scripts already carry `SHARK_MFA_ENCRYPTION_KEY` (P06). The "production smoke" command in the task brief needs it added.
- **Phase review items still open** remain as listed in each phase's review. For example: P02's e2e global setup only warns when the fake Razorpay sees unknown requests; P03's form idempotency key is not regenerated after a 409.
