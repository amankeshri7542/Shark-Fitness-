# P02: Razorpay payments in test mode — checkout, plan purchase, webhooks, refunds, payment links, reconciliation

## Summary

Members can pay an open invoice, buy a first plan or renew an expired/cancelled one, and staff can issue Razorpay payment links and provider refunds. Everything runs through **Razorpay test mode**: config refuses any key id that does not start `rzp_test_`, in every environment. Provider money settles through the single existing settlement path (receipt, dunning stop, membership activation, audit as `system:razorpay`, realtime) only when Razorpay confirms a **captured** payment, at most once. Webhooks are verified over the raw body, stored before processing, idempotent and safe in any delivery order. A 6-hourly `reconcile-payments` job settles what webhooks missed, and mismatches land in a Reconciliation panel. Without the Razorpay variables, behaviour is unchanged: members pay at reception and every member checkout endpoint answers 412 with the same message as before.

## Decisions and assumptions

- Signature checks are sync (pure HMAC); all network methods async. Port gained `fetchOrderPayments`/`fetchPaymentLink` for reconciliation.
- Dunning stays network-free: no mandates exist. Outcome codes without a provider are byte-for-byte unchanged.
- Live mode requires a reviewed code change, not a flag. `SHARK_RAZORPAY_API_BASE` only accepts Razorpay or loopback.
- One live order per invoice and amount; repeated taps or tabs resume it. Mismatched captures never settle (`needs_review` + exception; member told not to pay again).
- Provider refunds stay pending until `refund.processed`; membership reversal happens on processed. Dashboard refunds are recorded from the signed webhook and flagged for staff.
- Unrouted webhook events are stored with an empty tenant; unconfigured webhook endpoint answers 412; processing failures answer 503 so Razorpay retries.
- Retired `/checkout-intent` endpoints kept (always 412) so the existing boundary tests pass unchanged.
- Members never get eligibility approval assumed; plans needing approval or a corporate sponsor are not offered.
- Drop-in fees are still collected at reception (no drop-in invoice exists).
- No new dependencies.

## Independent review

An independent reviewer read the full diff, re-ran every gate, and probed the money paths against the fake Razorpay. Full report: `phases/P02-review.md`. **Verdict: ready for PR, with known minor issues.**

Correction to the results above: the first full `pnpm test` in review was **not** green. `apps/api` failed 958/959 on a flaky P01 test (`phase3-stabilization` random member numbers colliding with enrollment's max+1). Now fixed.

Fixed on this branch, each with a regression test that fails before the fix:
- **Major:** "Try again" (same Idempotency-Key) handed back a payable order after the invoice was paid at the desk, voided or part-paid, so the member could pay twice. A keyed retry now re-checks the invoice: paid or void → 409, a changed amount retires the old order (`ef8b9c5`).
- **Major:** a provider refund that timed out stayed `pending` forever once the refund sheet closed, holding its amount out of the refundable balance. `reconcile-payments` now resends it with the same `X-Refund-Idempotency` key (`de24765`).
- **Major:** payment links (and Checkout orders) stayed "active" and copyable after a desk payment or void. Settlement and void now retire stale attempts, and the drawer never offers a link on a non-payable invoice (`dc8ca83`).
- **Major:** the `payment.authorized` webhook and confirm captured money for attempts already retired, which then needed a manual refund. They now capture only for live attempts (`e895a80`).
- **Minor:** balances under ₹1 are refused up front instead of failing at Razorpay with "try again" (`ef8b9c5`). The reconciliation list fails closed for an empty branch scope (`2ffa570`). Flaky P01 test fixed (`2672875`). Docs updated (`281e058`).

Remaining (follow-ups): a retired link stays payable at Razorpay until it expires (needs a cancel-link port method; meanwhile that money lands in Reconciliation). The e2e setup only warns, rather than fails, when the fake Razorpay sees an unserved request. Two simultaneous first checkouts with different keys can open two orders (the second payment becomes an exception, not a double settlement).
